# Docs snippet tests: learnings

Lessons collected from agent runs. Read this before working on a page.
Entries are added only after the user approves them (agents propose them in their final report).

## Setup and tooling

- To probe API behavior quickly, write a throwaway vitest file under `test/docs-snippets/client/` that logs each call's result or error. It still runs the leak check, so register what it creates, and delete the file before finishing.
- Fences containing `import ... from "stream-chat"` can be regions: `stream-chat` is aliased to `src` (vitest `resolve.alias` + tsconfig `paths`). Put the region at module level, below the other imports, with the values it uses (e.g. `const apiKey`) declared above it, since a `const` after it would be in the TDZ. Example: `client/02-init_and_users/02-init_and_users.test.ts`. Don't `#docs-ignore` these fences.
- `StreamChat.getInstance` is a singleton for the whole test file. To run another `getInstance` snippet with different options, reset it outside the region: `Reflect.set(StreamChat, '_instance', undefined)`.
- Strict `types-docs` flags optional response fields: e.g. `getAppSettings()` types `app` as optional, so read `app?.field` (TS18048 otherwise).
- If a snippet calls SDK methods without awaiting or keeping the result (e.g. `channel.queryMembers({...});`), `vi.spyOn(obj, 'method')` before the region, await `spy.mock.results.map((r) => r.value)` after it to assert on the responses, then `spy.mockRestore()` (a second `spyOn` on the same method returns the old spy with its call history).
  - If the region creates its own instance (e.g. `const channel = client.channel(...)`), there's nothing to spy on beforehand: spy on the prototype (`vi.spyOn(Channel.prototype, 'update')`).
  - Destructuring awaited results with a default (`const [x = []] = await Promise.all(spy.mock.results.map((r) => r.value))`) loses the element type (TS7006); use `.flat()` on the results instead. Plain `await Promise.all(spy.mock.results.map(...))` is `any[]`: annotate the destructuring with the response type (`const [a, b]: QueryReactionsAPIResponse[] = ...`).
- `retry(fn)` (`helpers/wait.ts`) takes `() => Promise<T>`. A callback with only synchronous `expect`s fails `require-await` if marked `async`: write `() => { expect(...); return Promise.resolve(); }`.
- To test a snippet that starts with `client.connectUser(user, token)`, don't use `getClientSideClient`: build an unconnected `new StreamChat(process.env.STREAM_API_KEY as string, { allowServerSideConnect: true })`, upsert the user first, and seed state server-side before connecting (e.g. a pre-muted channel) so the connect response has something to assert on. Example: `client/03-channels/07-channel_management/10-muting.test.ts`.
- `vi.mock` in a test file doesn't affect modules `setup.ts` already imported (src and its deps). To mock one, call `vi.resetModules()` and re-import src dynamically (`await import('../../../../src')`).
- Upload snippets with browser `File`s fail under Node (the SDK's `form-data` path only takes streams/Buffers and detects `File` only when `window` exists). Run them with `vi.mock('form-data', () => ({ default: globalThis.FormData }))`, `vi.stubGlobal('window', { File, Blob })` in `beforeEach` (`vi.unstubAllGlobals()` in `afterEach`) and a client built from a fresh src import (see above). Example: `client/04-messages/02-file_uploads.test.ts`.
- A marker's `heading` is the nearest heading of any level above the fence, including `####` subheadings. When `test-docs-sync` reports "no such fence", it lists the correct key.
- To check state between two calls inside one region, wrap the first call: capture `const original = obj.m.bind(obj)` before the region, then `vi.spyOn(obj, 'm').mockImplementation(async (...args) => { const r = await original(...args); /* expect */ return r; })`.
- Fences that log from event handlers (`console.log("…", event.x)`): `vi.spyOn(console, 'log').mockImplementation(() => undefined)` before the region, trigger the events after it, `retry` until the expected call appears, and restore the spy in a `finally`.
- Placeholders a fragment uses (`filter`, `sort`, `next`, ...) are defined outside the region: type them with the SDK types (`ReminderSort`, `ReminderFilters`, ...) so literals don't widen, and compute cursors from real queries.

## API and SDK behavior

- Since v9, channel `name` (and other fields like `image`) are custom data, not in `ChannelData`/`ChannelResponse`. `test/docs-snippets/custom-types.d.ts` augments `CustomChannelData` with `name`, so snippets passing `{ name }` typecheck as-is. If a snippet needs another custom field, add it there, using the matching interface (`CustomMemberData` for member fields like `code_name`, etc.); no casts or typed client views in tests. Custom event types (`type: "friendship_request"`) go in `CustomEventTypes` and their payload fields in `CustomEventData`; `channel.sendEvent` needs a watched channel.
- To prove a channel is watched, check that its events reach the client: subscribe with `channel.on('message.new', ...)`, send a message server-side, and await the event. `client.activeChannels[cid]` proves nothing (`client.channel()` adds the channel there before any `watch()`), and `channel.watch()` returns `watchers` only when a watchers limit is requested.
- To check what one member sees (per-member truncation, `clear_history`, hidden history), query server-side as that member: `queryChannels({ cid }, {}, { user_id, message_limit: 10 })` returns their view of `state.messages`.
- `connectUser`, `connectAnonymousUser` and `setGuestUser` resolve to `void | ConnectionOpen` (`undefined` when a healthy connection already exists). A snippet reading `response.me` fails `types-docs` with TS18048: fix the docs (`response?.me`), not the SDK type.
- `team_id` and multi-tenancy: with multi-tenancy off, any `team_id` is rejected ("team_id is not supported when multi-tenancy is not enabled", code 4); with it on, client-side calls must pass it ("team_id is required when multi-tenancy is enabled"). Snippets with and without `team_id` need separate phases (e.g. a nested `describe` that turns multi-tenancy on and restores it).
- Toggling `multi_tenant_enabled` is eventually consistent across API nodes (a few seconds; one node returned the old value after 5 matching reads). Poll `getAppSettings` until ~20 consecutive reads agree, both after enabling and after restoring.
- `disable_auth_checks` (needed for `devToken` snippets) can be toggled now that the app is in development mode; save and restore it. The WS edge accepts dev tokens later than `getAppSettings` reports the new value (`connectUser` fails with 401 code 5 "development tokens are not allowed for this application"): after enabling, retry a throwaway dev-token `connectUser` outside the region until it succeeds (see `waitForDevTokensAccepted` in `client/02-init_and_users/01-client_tokens_and_authentication.test.ts`).
- Predefined filters: `createPredefinedFilter({ name: uniqueId(...), operation: 'QueryChannels', filter: {...} })` is usable immediately, client-side and server-side. Register `cleanup.add(() => serverClient.deletePredefinedFilter(name))` and put the docs' filter name in a COPY variable.
- `$and`/`$nor` (`ArrayOneOrMore`) and `$or` (`ArrayTwoOrMore`) are tuple types. A filter stored in a `const` is inferred as a plain array and isn't assignable to `ChannelFilters`. If the region is only the filter fragment, run it after the region via the raw endpoint (`client.post(`${client.baseURL}/channels`, { filter_conditions, ... })`) instead of casting.
- `client.channel(type, id, data)` only builds a local object. A snippet that goes straight to `updatePartial`/`update`/... on a new id fails with 404 code 16 "Can't find channel": that's a docs bug, fix it by adding `await channel.create()` to the snippet.
- Partial updates accept dot-notation nested paths (`set: { "channel_detail.topic": ... }`, `unset: ["channel_detail.rating"]`). `PartialUpdateChannel` and `PartialMessageUpdate` type them via `NestedFieldPath` in `src/types.ts`; the user/member partial-update types may need the same type fix when their pages come up.
- Request payload fields typed as response types (e.g. `message: MessageResponse` in `UpdateChannelOptions`) make snippets passing `{ text }` fail with TS2322 "'id' is missing": fix the SDK type to the request type (`Message`), not the docs.
- Sort objects stored in a variable before the call (`const sort = { last_message_at: -1 }`) fail strict TS: `-1` widens to `number`, and `ChannelSort`/`MemberSort`/... want `1 | -1`. Fix the docs by inlining the arguments into the call: inline all of them (filter, sort, options), not only the sort, e.g. `queryChannels({ type: "messaging" }, [{ last_message_at: -1 }], { limit: 15 })`. The same applies to `let` variables the snippet reassigns with a different shape (`options = { created_at_before }` after `{ user_id_lt }` fails with TS2353): use one call per value. Keep a variable only when the snippet uses it more than once or is a bare fragment with no call. Don't use `as const` (fences are plain JS) and don't widen the SDK type. The same widening hits any literal-union field in a stored object, e.g. `const message = { type: "system" }` then `sendMessage(message)` (TS2345, `string` not assignable to `MessageLabel`): inline the object into the call.
- Re-adding an existing member with `addMembers` is a silent no-op: new custom data or `channel_role` is ignored. Use `updateMemberPartial`, or add a different user.
- `channel.archive()` / `unarchive()` and `pin()` / `unpin()` work client-side for the connected member; they return the updated member with `archived_at` / `pinned_at` set or cleared.
- To assert per-user state with the server client, `queryChannels` with per-user filters (`muted`, `archived`, `pinned`, `hidden`, `invite`) needs `{ user_id }` in options (`muted` without it: "muted requires a valid user", code 4); it works without a `members` filter.
- `channel.hide()` / `show()` work client-side. A hidden channel reappears in `queryChannels` after a new message, but not instantly: wrap that check in `retry`.
- `skip_truncate` (`channel.delete` / `deleteChannels`) is server-only, and client-side it is silently ignored (200 OK, history still truncated). It only works on distinct channels that weren't truncated before (code 4 otherwise). Remove it from the `JavaScript` tab.
- Freezing (`frozen` in `update` / `updatePartial`) needs `UpdateChannelFrozen`, which a channel creator (`channel_member`) lacks (403 code 17): for client-side tests, `addModerators([userId])` server-side in `beforeAll`. To prove a channel is frozen: `sendMessage` resolves with `message.type === 'error'` (it doesn't throw) and `sendReaction` rejects with code 17 "...frozen...", for channel moderators too.
- `channel.truncate()` works client-side for the channel creator (`messaging`). A whole-channel truncate sets the channel's `truncated_at`; a later truncate with an earlier `truncated_at` fails ("must be more recent than previous one"), so use a fresh channel per tab group that passes `truncated_at`.
- Invites: a `messaging` channel creator can `inviteMembers` client-side, and the invited user can `acceptInvite()` / `rejectInvite()` on `client.channel(type, id)` without `watch()`. Check a member's invite state with server-side `channel.queryMembers({ user_id })`: invited = `invited: true` + `status: 'pending'`, accepted = `invite_accepted_at` + `status: 'member'`, rejected = `invite_rejected_at` + `status: 'rejected'`. To prove `queryChannels({ invite })` filters, give the user one accepted, one rejected and one pending channel in `beforeAll` and assert each query returns only its own.
- Batch updates (`channelBatchUpdater()`, `updateChannelsBatch`), `getTask` and `undeleteMessage` are server-only (403 code 17 "this endpoint can only be called server side"): remove them from `JavaScript` tabs.
- In the test app, `messaging` doesn't grant `channel_member` `create-attachment`, `create-mention`, `create-system-message` or `notify-here`/`notify-channel`/`notify-role`/`notify-group`: client-side attachments, `type: "system"` messages or `@here`/`@channel`/role/group mentions fail with 403 code 17 ("not allowed to perform action CreateAttachment/NotifyHere...", "creating system messages not allowed"). Add them to `messaging` with `grantMessagingMembers(serverClient, cleanup, [...])` (`helpers/grants.ts`, registers the restore) followed by `waitForChannelTypePropagation()`; don't create a separate channel type. Example: `client/04-messages/01-send_message.test.ts`. Uploading itself (`channel.sendImage`/`sendFile`, `client.uploadImage`, `deleteFile`/`deleteImage`) needs no extra grant: only sending a message with attachments needs `create-attachment`.
- Client-side `deleteChannels` returns a synchronous `result: { [cid]: { status } }` and no `task_id` (the `task_id` shape is server-side only).
- `channel.deleteReaction()` calls `_checkInitialized`, so the channel must be watched (`sendReaction` doesn't need it).
- `channel.muteStatus()` throws "hasn't been initialized yet" unless the channel is watched (fix the docs with `await channel.watch()`). It reads `client.mutedChannels`, which only updates on the `notification.channel_mutes_updated` WS event, not from the `mute()` response: poll it with `retry` after the region.
- Stream CDN URLs are re-signed on every read: compare a stored `image`/asset URL with the uploaded one without the query string.
- `ThreadManager` (`client.threads`): `loadNextPage()` is a no-op on a fresh manager (`nextCursor` starts `null`); the first page needs `reload()` (fix the docs). Once the manager is `ready`, `reload()` is a no-op too, so use a fresh client per snippet that loads it.
- A thread's `created_by_user_id` is the author of its first reply, not of the parent message: for `queryThreads({ filter: { created_by_user_id } })`, have the same user write both.
- Thread read state works client-side on a watched channel: `channel.markRead({ thread_id })` / `markUnread({ thread_id })`. Check it with `client.getUnreadCount()` (`threads[]` entries with `parent_message_id` and `unread_count`); it updates immediately, no retry needed.
- Timestamps the docs set (e.g. `pin_expires: "2077-01-01T00:00:00Z"`) can come back with sub-second digits: assert with a prefix match (`toMatch(/^2077-01-01T00:00:00/)`), not `toBe`.
- `client.search` works client-side, but indexing is eventually consistent: in `beforeAll`, `retry` a search until all seeded messages come back, then run the snippets. Retrying the snippet region itself doesn't work.
- To prove something does NOT change (e.g. a silent message doesn't raise the unread count), add a positive control: compare `serverClient.getUnreadCount(otherUserId)` before and after the snippet, then send a regular message and assert the count goes up by 1. Unread counts update immediately, no retry needed. For an event that must NOT be sent (e.g. `message.read` with `read_receipts` disabled), let a watcher record events, have the tested user act, then a control user, and `retry` until the control's event arrives: WS events come in order, so the tested user's event would already be there.
- Per-channel feature flags (e.g. message reminders: "reminders are not enabled for this channel", code 4): enable them on the test channel with server-side `channel.updatePartial({ set: { config_overrides: { user_message_reminders: true } } })` instead of changing the channel type; nothing to restore.
- `BasePaginator`-based managers (`client.reminders.paginator`, ...) catch query errors into `state.lastQueryError` instead of throwing: assert it's `undefined` after `queryNext…`/`queryPrevious…`.
- Events without a `cid` (`user.presence.changed`, `connection.changed`, ...) never reach `channel.on(...)`: `client.dispatchEvent` routes to channel listeners by `cid` only. A `JavaScript` snippet listening for them on a channel is a docs bug (use `client.on`).
- Presence: watch the channel with `{ presence: true }` as user A, then connect user B with `getClientSideClient` and disconnect it: A gets `user.presence.changed` with `online: true`, then `false`, within a second or two.
- To trigger `connection.changed` client-side: `client.wsConnection?.onlineStatusChanged(new globalThis.Event('offline'))` (`online: false` ~5s later), then `'online'` to reconnect (`online: true`). `closeConnection()`/`openConnection()` only emit `online: true`. Use `globalThis.Event`: the `Event` type from src shadows the DOM name.
- Listeners a snippet registers without keeping the unsubscribe leak into later tests: use a fresh watched channel per test and reset `channel.listeners = {}` in `finally`; for `client.on`, `vi.spyOn(client, 'on')` and call `unsubscribe()` on the `mock.results` values.

## Client-side vs server-side

- Server-only `JavaScript` snippets (they fail with a user token) are removed from the page. Don't add a `Node.js` tab for them (`Node.js` fences are out of scope). If only part of a snippet is server-only (e.g. setting `channel_role` in `updateMemberPartial`), remove just that part from the `JavaScript` tab and keep the rest.
- If every `JavaScript` fence of a page turns out to be server-only (all removed), don't write a client test file: a test that only asserts the user-token rejection covers no docs snippet. Record the error in the report instead.
- Acting-user fields (`user_id`, `user: { id }`, `created_by_id`, a `userId` option saying who performs the action): remove one from a `JavaScript` snippet only if the client-side OpenAPI spec doesn't list it on that endpoint's request. Check `chat-clientside-api.json` (`gh api -H 'Accept: application/vnd.github.raw' repos/GetStream/protocol/contents/openapi/v2/chat-clientside-api.json`): find the operation, follow the `requestBody` `$ref`s, and cite the operation id + schema in the report. If the client spec has the field, keep it and test it. Example: `SendMessage`'s client `MessageRequest` has no `user`/`user_id` (the server one does), so `user: systemUser` is removed from `sendMessage` snippets. Don't decide by probing: some endpoints silently ignore the field and act on the connected user (e.g. `channel.mute({ user_id })`). `user_id` as data is fine (filter values, member lists like `addMembers([{ user_id }])`, sort keys).
- Member role changes are server-only: client-side `addModerators`/`demoteModerators` fail with 403 code 17 ("changing channel member roles is not allowed client-side"), and `updateMemberPartial` with `channel_role` fails with code 17 ("this channel role can only be updated server side"). Client-side `updateMemberPartial` of custom fields works for the connected user without a `userId` option (don't pass one client-side: another user's id fails with 400 code 4, and your own is redundant). Client-side `addMembers([{ user_id, channel_role }])` for a new member does work (channel owner, `messaging`).

## Docs conventions

- Undefined app-supplied placeholders (e.g. `tokenProvider`) aren't docs bugs: define them in the test just before the region (e.g. `const tokenProvider = () => Promise.resolve(serverClient.createToken(userId))`, which also satisfies `require-await`), and don't change the docs.
- A fence that declares the same `const` twice (e.g. two `const result = ...` or `const filter = ...` showing alternatives) is a real SyntaxError and TS2451. Fix the docs by renaming only the later declarations with descriptive names (`aroundResult`, `membersFilter`); don't split the fence.
- A fence showing alternative operations on one placeholder id (e.g. soft delete, hard delete, delete for me on `messageID`) can fail when run in sequence (delete-for-me after a hard delete: 404 code 16). Fix the docs by giving the conflicting later call its own id (`anotherMessageID`); don't split the fence.
- Comment-only `JavaScript` fences ("This is a server-side only feature, choose any of our server-side SDKs...") stay in the docs: mark them `#docs-ignore` with `reason="comment-only placeholder: ... is server-side"`.
- When the docs use an identifier (not a string literal) like `randomID`, name the test variable the same and don't put it in COPY. A quoted COPY value (`randomID="randomID"`) turns it into a string literal, and `DOCS_SYNC_WRITE` then silently writes the quoted string into the docs.

## Isolation and cleanup

- Distinct channels (no id) get an auto id `!members-...`: push `channel.cid` to `cleanup.channels` right after `create()`/`watch()`, and use `uniqueId` members.
- Guest users: push `client.userID` (the rewritten `guest-<uuid>-<id>`) to `cleanup.users` in a `finally` around the snippet, so it is cleaned up even if a later assertion fails.
- Some names are unique per app (e.g. user group names: `a group with name "Design Team" already exists`), and the leak check matches by id or name. Use a COPY variable from `uniqueId` for every such `name`, including the new name in update/rename snippets.
- Server-side `deleteUsers` of an id that was never created succeeds, so register a user on `cleanup` before the snippet creates it.
- Polls and campaigns are NOT deleted when their creator user is hard-deleted. Delete them explicitly via `cleanup.add(...)` (`deletePoll(id, userId)` needs a `user_id` server-side; `deleteCampaign(id)`), and give campaigns a `uniqueId(...)` name so the leak check can find them.
- To assert ordering or offset pagination exactly, create ~12 channels in `beforeAll` and send one message to each, sequentially (not `Promise.all`): `last_message_at: -1` order is then the reverse of creation order. Same for message pagination (`id_lt`/`id_around`): send ~30 messages sequentially, record their ids in order, and compare pages to exact slices.
- To assert member `created_at` order or `created_at_before` pagination, add members one at a time with `addMembers([id])` in `beforeAll`: members passed together to `create()` can share a `created_at`.
- To prove a "flagged first" sort (e.g. `pinned_at: -1`) is applied, flag a channel first and create a second channel after it: without the sort the newer one comes first, so `toEqual([flagged, other])` shows the sort worked.
- `cleanup.add` steps run after `disconnectClients`, so they can't use a user client ("Both secret and user tokens are not set"). Standalone uploads (`client.uploadImage`/`uploadFile`) aren't removed with the user or channel and the leak check can't see them: delete them in the test while the client is connected.
